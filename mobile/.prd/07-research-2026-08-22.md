## 1. 앱이 무엇인가

herdr의 도메인은 **remote ▸ workspace(space) ▸ tab ▸ pane(=terminal)**이고, agent는 pane 위에 얹힌 논리 뷰다(`AgentInfo`가 `workspace_id`/`tab_id`/`pane_id`를 모두 들고 있다 `[i] src/api/schema/agents.rs:184-232`). 폰에서는 이 4단 트리를 **3단 내비게이션 + 1개의 횡단 뷰**로 접는다: ① 리모트 목록(= 내가 가진 서버들) → ② 워크스페이스 목록(각 행에 idle/working/blocked 롤업) → ③ pane 뷰어(탭 스트립 = herdr tab, 그 안의 split pane은 세그먼트로 평탄화) — 그리고 이 트리를 가로지르는 **Agents 화면**(`agent.list` 한 방으로 전 서버 에이전트를 상태순 정렬)이 앱의 헤드라인이다. 폰에서 사람이 실제로 하는 일은 "누가 나를 기다리나(blocked) → 그 화면 보고 → y 눌러주기"이므로, 트리 브라우징이 아니라 **Agents 화면이 홈**이고 pane 뷰어는 그 상세다.

**orca와 같은 것**: master-detail 레이아웃과 프로토콜 게이트 `[i] mobile/app/h/_layout.tsx:141-161`, host당 공유 클라이언트 1개 패턴, xterm.js-in-WebView 렌더러, transport 생존성 4층, 설정/트러블슈팅/연결로그 화면.
**다른 것**: (a) orca는 tab=terminal 1:1이라 **split/pane 레벨이 아예 없다** — 이 한 단계는 신규 설계다. (b) orca의 pairing/E2EE/relay 3종 세트는 통째로 사라진다. herdr은 인증이 ssh 자체고 와이어에 auth 필드가 없다 `[i] src/server/socket_paths.rs:12`. (c) orca의 `git.*`/`files.*`/tasks 화면(15k줄)은 herdr JSON API에 대응 메서드가 없어 v1에서 전부 드랍 — herdr에서 git은 pane 안에서 산다.

## 2. 아키텍처

### 2.1 두 채널

| | 컨트롤 플레인 | 데이터 플레인 |
|---|---|---|
| 브리지 | `herdr remote-api-bridge` `[v] src/remote/unix.rs:553-562` | `herdr remote-client-bridge` `[v] src/remote/unix.rs:542-551` |
| 포맷 | NDJSON `{id, method, params}` `[i] src/api/schema.rs:36-47` | `[u32 LE len][bincode payload]` `[i] src/protocol/wire.rs:1136-1155` |
| 담당 | 열거·네비게이션·에이전트·**입력**·이벤트 | pane 화면 스트림 1개 |
| 수명 | 요청 1개 = 연결 1개(!) / `events.subscribe`만 상주 | 연결 1개 = pane 1개, 상주 |

두 브리지 모두 unix 소켓 ↔ stdio 순수 바이트 펌프다 `[v] src/remote/unix.rs:542-562`. 서버 쪽에 새로 만들 컴포넌트가 없다는 뜻이고, 동시에 **인증 경계가 전적으로 ssh**라는 뜻이다.

### 2.2 ssh 계층 — orca 대비 최대 신규 작업

orca는 WebSocket이라 RN 기본 기능으로 끝났다. herdr은 ssh exec 채널이 필요하다. RN에는 표준 ssh 스택이 없으므로 **네이티브 모듈 1개**(iOS: libssh2/NMSSH, Android: sshj)를 직접 싸야 한다. 계약:

- transport 1개(호스트당) + **채널 N개**. 새 TCP 다이얼 금지 — herdr 데스크톱이 이미 같은 문제로 `ControlMaster=auto/ControlPersist=60`을 주입해 우회한다 `[i] src/remote/unix.rs:310-330`(측정치: ~2.5 fresh sshd conn/sec).
- 상주 채널 2개: `remote-client-bridge`(현재 보고 있는 pane) + `remote-api-bridge`에 핀 고정한 `events.subscribe`.
- 단발 채널: JSON API 호출 1개당 1개 (§3-B8이 해소되기 전까지).
- keepalive는 herdr이 이미 세팅한 `ServerAliveInterval=15 / CountMax=4` `[i] src/remote/unix.rs:295-308`를 그대로 쓰되, 검출까지 ~60초라 앱 레벨 워치독(§5 L1)을 위에 얹는다.

### 2.3 렌더러 — TerminalAnsi 경로 (권장 기본값)

Hello의 `requested_encoding`은 협상되지 않고 Welcome에 그대로 echo된다 `[i] src/server/client_transport.rs:614-619`. 그리고 `ClientRenderState`는 encoding으로만 갈라지고 `[v] src/server/render_stream.rs:27-28`, `prepare_frame`의 TerminalAnsi 분기는 `BlitEncoder`로 diff해서 `ServerMessage::Terminal(TerminalFrame{seq,width,height,full,bytes})`를 만든다 `[v] src/server/render_stream.rs:105-120`. 이 인코딩은 **연결 모드와 직교**하므로, TerminalAttach/TerminalObserve 클라이언트가 요청해도 동일하게 적용된다 — 렌더 dispatch는 모드로 FrameData를 만들고 `[v] src/server/headless.rs:4152-4168`, 그 뒤 encoding으로 직렬화한다 `[v] src/server/headless.rs:4237-4240`.

결과:

```
Hello{ v20, cols, rows, cell_px 0/0, TerminalAnsi, FullApp(filler), Server, TerminalAttach }
→ Welcome
→ ObserveTerminal{ target: "w1:p3" }
→ Terminal(TerminalFrame{ bytes: <ANSI> }) 스트림
→ xterm.js WebView.write(bytes)
```

앱이 손으로 써야 할 bincode 디코더는 **envelope + Welcome + Terminal 3개뿐**이다(스칼라 varint + `Option<String>` + `Vec<u8>`). `CellData`/`FrameDelta`/FNV-1a 체크섬/DEFLATE 전부 불필요. 이게 SemanticFrame 경로 대비 절감하는 양이 크다 — 조사 리포트가 지적한 JS 쪽 난제(u64 체크섬, per-cell 객체 churn, raw deflate)가 통째로 사라진다 `[i] wire-codec-spec §11`.

**트레이드오프**(§6 열린 결정 1): TerminalAnsi는 앱이 자체 UI로 셀을 그릴 수 없고 xterm에 종속된다. 하이퍼링크/그래픽/선택 복사는 xterm 애드온에 맡긴다.

### 2.4 쓰기 경로 — 와이어를 쓰지 않는다

`ControlTerminal`/`AttachTerminal`은 PTY를 폰 그리드로 **resize하고 락을 건다** `[v] src/server/headless.rs:2665-2675`. 데스크톱 파괴다. 반면 `ObserveTerminal`은 resize도 락도 없다 `[v] src/server/headless.rs:1763-1786` — 대신 입력이 조용히 버려진다 `[i] src/server/headless.rs:2882-2887`.

**해법: 읽기는 와이어(observe), 쓰기는 JSON API.** `pane.send_input {pane_id, text?, keys?}` `[i] src/api/schema/panes.rs:242-249`는 attach와 무관한 일반 메서드다. 소프트 키보드의 IME 텍스트는 `text`로, Enter/Ctrl-C/화살표는 `keys[]`로. 즉 **v1은 `ControlTerminal`을 아예 쓰지 않는다** — 그러면 그리드 락, takeover 경쟁, stale attach 미회수(§3-B7) 세 블로커가 동시에 사라진다.

남는 것: 스크롤백(observe는 `AttachScroll` 불가 `[i] src/server/headless.rs:1802-1806`)과 마우스 리포팅. 이건 M6로 미룬다.

## 3. 선행 차단 요소 (herdr 쪽이 먼저 바뀌어야 하는 것)

### B1. PROTOCOL_VERSION 완전일치 — 최우선, 나머지는 전부 이것 다음이다

- **무엇이 막나**: `pub const PROTOCOL_VERSION: u32 = 20` `[v] src/protocol/wire.rs:23`. `check_client_version`은 `client_version == PROTOCOL_VERSION`만 통과시키고 older/newer 둘 다 `Incompatible`로 떨어뜨린다 `[v] src/protocol/wire.rs:1218-1237`. 서버는 Welcome에 error를 실어 보내고 소켓을 닫는다 `[i] src/server/client_transport.rs:557-570`. 브리지 경로도 같은 게이트를 통과해야 한다 — `ensure_remote_server_running`이 `status.protocol == CURRENT_PROTOCOL`을 강제한다 `[i] src/remote/unix.rs:600-606`.
- **왜 앱에 치명적인가**: 데스크톱 CLI는 서버와 같이 업그레이드된다. **앱스토어 바이너리는 그럴 수 없다.** 측정된 범프 주기는 79일 11회 = ~7.2일/회인데(오케스트레이터 측정), TestFlight 외부 배포도 심사가 있고 App Store는 더 길다. 유저가 자기 맥에서 `git pull`을 한 번 하면 폰의 앱이 그 순간 벽돌이 된다. **이건 앱의 성능 문제가 아니라 존재 조건이다.**
- **고치는 범위**: herdr-mx#70이 이미 제안한 `MIN_SUPPORTED_PROTOCOL..=PROTOCOL_VERSION` 창 `[v] gh issue view 70 = OPEN, "Fleet upgrade window"`. 구현은 `check_client_version` 한 함수 + 상수 1개 + 브리지의 등호 비교 1곳. **단, 창만으로는 부족하다** — `FrameData`/`TerminalFrame`은 위치기반 bincode 구조체라, 창이 N-1을 받아준다면 **그 창 안에서 어떤 구조체 레이아웃이 동결되는지도 같이 선언**해야 한다. TerminalAnsi 경로를 택하면 동결 대상이 `TerminalFrame{seq,width,height,full,bytes}` 5필드로 줄어 이 부담이 크게 작아진다(이것도 TerminalAnsi를 고르는 이유다).
- **정책은 orca에서 베낀다**: 클라가 `MOBILE_PROTOCOL_VERSION` + `MIN_COMPATIBLE_SERVER_VERSION`을 선언하고, 서버가 자기 버전 + min-compatible-client를 광고하고, `evaluateCompat`이 `{blocked, reason: 'mobile-too-old'|'server-too-old'}`를 내서 **하드 블록 화면**으로 보낸다 `[i] mobile/src/transport/protocol-compat.ts:18-41`. 범프 정책도 명문화: 옵셔널 필드 추가는 범프 아님 `[i] mobile/src/transport/protocol-version.ts:11-13`. orca는 이 규율로 앱 출시 후 버전 3에 머물러 있다.

### B2. ServerMessage 와이어 태그 동결 테스트 부재

- **무엇이**: ClientMessage에는 태그 순서를 고정하는 테스트가 있다 `[i] src/protocol/wire.rs:1382-1454`. ServerMessage에는 **없다** — 태그는 선언 순서일 뿐이다 `[i] src/protocol/wire.rs:797-895`.
- **왜 치명적**: upstream 머지가 enum 중간에 variant를 하나 끼우면 `Welcome=0`/`Terminal=13`이 조용히 밀리고, 앱은 실패가 아니라 **오파싱**한다. 대응 코드가 v0.8.0 안에 이미 있다는 게 증거다 — "mx 와이어 태그가 안정되도록 꼬리에 붙였다"는 주석 `[i] src/protocol/wire.rs:884`.
- **범위**: ClientMessage 테스트의 미러 1개. 30줄. 앱 착수 전에 머지되어야 한다.

### B3. 컨포먼스 픽스처 부재

- **무엇이**: 전 리포에 동결된 골든 바이트가 `ClientMessage::InputEvents` 하나뿐이다 `[i] src/protocol/wire.rs:1513-1522`. Welcome/Terminal/Frame에 대한 것은 없다.
- **왜 치명적**: TS 코덱이 실패할 수 있는 RED 테스트가 없다는 뜻. 범프마다 양쪽 손수정이 된다.
- **범위**: `#[test]`가 hex/JSON 코퍼스를 `docs/next/protocol/fixtures.json`으로 뱉게 하고(JSON Schema 아티팩트가 이미 같은 방식으로 CI 강제된다 `[i] src/api/schema/tests.rs:152-175`), TS 쪽 vitest가 그 파일을 읽어 검증. 하루짜리.

### B4. observe는 리플로우가 아니라 좌상단 크롭

- **무엇이**: 렌더는 `while y < area.height && rows.next()` 식으로 잘린다 `[i] src/pane/terminal.rs:1956-1962`. observe는 PTY를 리사이즈하지 않으므로 `[v] src/server/headless.rs:1763-1786`, 40컬럼 폰이 200×50 pane을 보면 좌상단 40×N만 보인다 — 커서와 최근 출력이 화면 밖.
- **왜 치명적**: 읽기 화면이 v1의 전부인데, 그게 잘린 코너를 보여준다.
- **범위 / 완화**: (a) **서버 변경 없이**: xterm WebView를 **PTY 폭 그대로** 렌더하고 폰은 핀치줌/가로스크롤로 본다 — Hello의 cols/rows를 폰 해상도가 아니라 대상 pane의 실제 크기(`pane.get`으로 선조회)로 보낸다. 데스크톱은 안 건드린다(observe라서). 이게 v1 답이다. (b) 서버 변경: observe 클라이언트별 뷰포트 오프셋(follow-the-cursor 또는 bottom-anchored). CLI 스펙이 이미 `--cols/--rows`를 예고하고 있어 의도는 있다 `[i] src/cli/spec.rs:695-700`.

### B5. observe는 스크롤 불가

- **무엇이**: `handle_terminal_attach_scroll`이 `TerminalAttach`만 매치한다 `[i] src/server/headless.rs:1802-1806`.
- **왜**: 스크롤백을 못 본다. B4의 (a) 완화와 합치면 "보이는 화면 안에서는 다 보이지만 과거는 못 본다".
- **범위**: 매치를 `TerminalObserve`까지 넓히되 **공유 runtime을 스크롤하면 안 된다**(데스크톱 뷰가 같이 움직인다) — per-client 뷰포트 오프셋이 필요하므로 사실상 B4(b)와 같은 작업이다. v1은 xterm 자체 스크롤백 버퍼(orca는 5000줄 `[i] mobile/src/terminal/terminal-webview-html.ts:726-748`)로 대체한다.

### B6. 연결 모드는 1회 고정 — pane 전환 = 재연결

- **무엇이**: `client_is_pending_terminal_mode`는 `pending_terminal_attach && mode == App`을 요구하고 `[v] src/server/headless.rs:2679-2683`, 호출부는 정확히 두 곳(1732 = observe/control 공용 리졸버, 2579 = attach) `[v] grep`. 각 핸들러가 플래그를 내린다 `[v] headless.rs:1777, 2661`. 두 번째 타깃 요청은 실패가 아니라 **연결 종료**다 `[i] tests at headless.rs:6110, 6136`.
- **왜 치명적**: 앱의 핵심 동작이 "pane 스와이프 전환"인데, 매 전환마다 ssh 채널 스폰 + Hello/Welcome + 풀 프레임 베이스라인을 다시 낸다.
- **범위**: `ClientMessage::RetargetTerminal { target }`을 enum 꼬리에 추가(태그 14). 핸들러는 `resolve_terminal_session_target` 재실행 + `client.mode` 교체 + `render_state.reset_baseline()`. observe→observe만 지원하면 소유권/락 처리가 필요 없어 **~40줄**. 이걸 안 하면 앱은 pane당 채널을 미리 열어두는 프리페치로 우회해야 한다(비용은 sshd 부하).

### B7. stale attach 회수 없음 — **observe-only면 소멸**

- **무엇이**: 정리는 소켓 종료(ClientDisconnected)로만 일어나고 `[i] src/server/headless.rs:3061`, `last_activity`는 벽시계가 아니라 foreground 선택용 카운터다 `[i] src/server/clients.rs:284`. 백그라운드로 간 폰이 데스크톱 PTY를 자기 그리드에 무기한 고정할 수 있다.
- **완화**: §2.4대로 **ControlTerminal을 쓰지 않으면 이 블로커는 발생하지 않는다.** M6에서 제어를 도입할 때만 되살아나며, 그때는 (a) 앱 계약(백그라운드 진입 시 항상 `Detach`, 복귀 시 항상 `takeover:true`) + (b) 서버 idle timeout 둘 다 필요.

### B8. JSON API: 요청 1개 = 연결 1개

- **무엇이**: `handle_connection`은 한 줄만 읽고 응답 후 리턴한다 — 루프가 없다 `[v] src/api/server.rs:139-162` + 일반 arm이 write 후 return `[i] :258-283`. 실측으로 파이프라인 2개 중 1개만 응답 `[i] json-api-surface`.
- **왜 치명적**: 브리지 위에서는 **JSON 호출 1개 = ssh exec 1개 = 원격 herdr 프로세스 1개**, 게다가 매번 내부 `ping` 왕복까지 문다 `[i] src/remote/unix.rs:595`. 앱의 리스트 새로고침 한 번이 exec 수 개다.
- **범위**: `handle_connection`을 NDJSON 요청 루프로 바꾸고 `id`로 상관시킨다. 스트리밍 arm은 지금처럼 연결을 점유. **서버 ~50줄**, 앱 쪽 ssh 채널 수가 O(N)→O(1)로 떨어진다. 이게 없으면 앱은 단발 채널 폭풍을 쓰거나 폴링 주기를 크게 늘려야 한다.

### B9. events.subscribe: 시퀀스 없음 + 매번 전량 리플레이 + 10/s 상한

- **무엇이**: 봉투는 `{event, data}`뿐이라 갭 검출이 불가능하다 `[i] src/api/schema/events.rs:364-368`. 평범한 구독은 전부 `last_sequence: 0`으로 생성된다 `[v] src/api/subscriptions.rs:126,131,136,141,146` → 512칸 링버퍼 `[v] src/api/event_hub.rs:13`를 통째로 재생한다. 폴 루프는 100ms마다 구독당 **첫 매치 1건만** 쓴다 `[v] src/api/server.rs:29,693-708` → 구독당 10 events/s 상한. 예외는 `pane_id`가 지정된 agent-status 구독뿐(`current_sequence()`에서 시작 `[v] :298`).
- **왜 치명적**: 모바일은 재연결이 상시다. 매 포그라운드마다 51초/320KB짜리 과거를 먹으면서 라이브에 도달하지 못한다.
- **범위**: (a) `EventEnvelope`에 `sequence: u64` 추가, (b) `EventsSubscribeParams`에 `since: Option<u64>` / `from_now: bool`, (c) 요청 시퀀스가 이미 축출됐으면 `gap: true` 마커, (d) 폴 틱마다 매칭 전량 드레인. 서버 중간 규모 작업.
- **앱 쪽 임시 대응(서버 변경 전)**: 이벤트를 **상태로 신뢰하지 않는다.** 구독은 `from_now`가 없으므로 앱이 자체적으로 "구독 시작 시각 이전 것은 버린다"를 할 수 없다 → **v1은 구독 대신 `agent.list` 폴링(포그라운드 3–5초)** 로 간다. 구독은 B9 해소 후 도입.

### B10. `pane.read`는 변경검출에 못 쓰고, 유저 pane을 스크롤시킬 수 있다

- **무엇이**: `PaneReadResult.revision`이 4개 생성 지점 전부 하드코딩 0 `[i] panes.rs:1202, agents.rs:147, server.rs:1231, headless.rs:5958`. 그리고 와이어 `pane.read`는 `intent`가 `#[serde(skip)]`이라 항상 `Interactive`로 들어가 `[i] src/api/schema/panes.rs:261-263`, 조건이 맞으면 서버가 실제 alt-screen 스크롤 캡처를 돌린다 `[i] src/server/headless.rs:3164-3213`.
- **왜**: "폴링으로 pane 내용 읽기" v0 전략이 **유저의 살아있는 에이전트 pane을 물리적으로 스크롤시킨다.**
- **범위**: `intent`를 와이어에 노출하거나 와이어 기본값을 Passive로. 5줄. 이게 되기 전엔 앱이 `pane.read`를 반복 호출하면 안 된다 → **v1의 pane 화면은 반드시 observe 와이어 스트림**이고 `pane.read`는 1회성 프리뷰에만 쓴다.

### B11. 인증 = ssh 키 = 셸 전체 권한

- **무엇이**: 와이어에 auth 필드가 없고 `[i] grep over wire.rs`, JSON 소켓에는 핸드셰이크조차 없다 `[v] src/api/server.rs:139-162`. 통제는 0600 소켓뿐 `[v] :28`.
- **왜**: 폰이 잃어버려지면 그 키로 머신 셸이 열린다. herdr 수준의 스코프/폐기 수단이 없다.
- **범위(설계 결정, §6-4)**: (a) 앱 전용 키를 `authorized_keys`에 `command="herdr remote-client-bridge",no-pty,no-port-forwarding`으로 제한 — **서버 변경 0**, 단 두 브리지를 쓰려면 키 2개 또는 `SSH_ORIGINAL_COMMAND` 디스패치 래퍼 1개. 이게 실용적 답. (b) herdr에 페어링 토큰을 넣는 건 큰 신규 설계이므로 v1 범위 밖.

### B12. Windows 서버

`run_terminal_attach`가 Windows에서 `Unsupported` `[v] src/client/mod.rs:2558-2565`. observe 서버 핸들러 자체에는 cfg 게이트가 없어 보이나 `[추정]`, v1은 Unix 서버로 스코프를 명시한다.

## 5. orca에서 그대로 가져올 것 — transport 생존성 체크리스트

| X5 | 복귀 순간 N개 화면이 동시에 같은 새로고침 | (client, host, kind) 키의 single-flight + trailing follow-up `[i] request-single-flight.ts:10-19` | **그대로.** B8이 남아있는 동안엔 특히 필수 |
| X6 | 버전 불일치가 원인불명 재연결 루프로 보임 | 양방향 창 + 하드 블록 화면 `[i] protocol-compat.ts:18-41` | **그대로 = B1** |

## 6. 열린 결정 — 유저가 정해야 하는 것

1. **렌더러**: `TerminalAnsi` + xterm.js WebView(권장 — §2.3, 코덱 부담 최소, orca 코드 재사용 최대, 동결해야 할 구조체 5필드) vs `SemanticFrame` + 네이티브 셀 렌더러(자유도 높고 herdr UI 재해석 가능, 대신 bincode/FNV/deflate/델타를 전부 손으로 + 매 범프마다 유지보수). **한 번 고르면 되돌리기 비싸다.**
2. **v1 pane 뷰의 폭 정책**: PTY 폭 그대로 렌더 + 핀치줌(서버 변경 0, 지금 당장 가능) vs observe 뷰포트를 herdr에 추가(B4b, 폰에 딱 맞지만 서버 작업). 
3. **홈 화면**: Agents 우선(내 판단으로는 이게 맞다 — 폰에서의 실제 용도) vs 리모트/워크스페이스 트리 우선(orca 구조에 더 가까움).
4. **폰의 ssh 키 권한 범위**: 제한 없는 유저 키(간단, 분실 시 셸 전체) vs `authorized_keys`의 `command=` 강제 + 브리지 디스패치 래퍼(안전, 유저가 서버마다 한 줄 설치) — **B11. 내 권고는 후자, 다만 이건 유저의 위험 감수 결정이다.**
5. **배포 채널**: TestFlight 내부/외부만(심사 짧음, B1 압력 완화) vs App Store 정식. Android도 orca처럼 태그 분리해 별도 릴리즈할지 `[i] .github/workflows/mobile-*-release.yml`.
6. **`FullApp` 좁은폭 화면을 v1에 넣을지**: cols ≤ 64면 서버가 폰 모양 UI(2행 헤더 + 탭 서피스, Navigate가 전체화면 스위처)를 그려준다 `[v] src/config.rs:39, src/ui.rs:336` — 클라 레이아웃 작업 0으로 "전체 herdr UI" 화면이 하나 공짜로 생긴다. **단 `App` 런치모드 클라이언트는 접속 즉시 foreground가 되어 모든 pane PTY를 폰 그리드로 리사이즈한다** `[v] headless.rs:2825-2832` — 즉 이 화면을 켜는 순간 데스크톱이 폰 크기로 접힌다. 넣으려면 herdr에 non-foreground 앱-클라이언트 플래그(`claims_foreground: bool`)가 먼저 필요하고, 심지어 수동적으로 붙어도 **첫 탭이 foreground로 승격시킨다** `[v] headless.rs:2723-2730`. → **내 권고는 v1 제외.**
7. **푸시 릴레이 소유**: 2lab 인프라에 작은 HTTPS 릴레이를 세울지(APNs p8 JWT를 셸이 못 만든다), 아니면 M5를 아예 생략하고 포그라운드 폴링만 갈지.
8. **B8/B9 서버 수정을 M0에 넣을지**: 넣으면 앱이 훨씬 싸게 만들어지고 herdr JSON API 자체가 좋아진다. 안 넣으면 앱이 폴링+채널폭풍으로 우회하고 M6 이후로 미룬다.
